# LabFit KR 개발 계획 (원 계획서 이후 변경분)

원 계획서: `LabFit KR 해커톤 계획서 (1).pdf`. 이 문서는 구현하면서 바뀐 결정과 이후 계획만 적는다.

## 1. 구현하면서 바뀐 결정

| 항목 | 원 계획 | 현재 | 바꾼 이유 |
|---|---|---|---|
| 입력 | 연구 질문·방법·장비를 직접 입력 | **연구제안서 PDF 업로드** → 추출값을 폼에 채우고 학생이 확인·수정 (직접 입력도 유지) | 실제 사용 흐름. 확인 단계가 "장비 추정 확인"을 대신함 |
| 순위 | S = √(T×C) | **0.5·T(주제) + 0.5·M(방법)**, C(근거 문장)는 배지로만 | 초록 근거 C는 0이 많아 곱하면 후보가 사라짐. 실제 제안서에서 주제만 보면 연락 예정 교수(방법이 맞는 연구실)를 놓쳤음 |
| T 계산 | 상위 3편 유사도 평균 | s1 + 0.1·s2 + 0.05·s3 | 평균은 덜 관련된 논문을 여러 편 쓴 사람을 과하게 우대 |
| 검색 | 주제 검색어 | 주제 검색어 3개 + **방법·장비 검색어 2개** | 주제가 달라도 필요한 방법·장비를 가진 연구실을 후보 풀에 넣기 위해 |
| 데이터 소스 | OpenAlex (+KCI·NTIS 검토) | OpenAlex + **DBpia 공개 영역(비공식, 로그인 없음)** 별도 섹션 | KCI·NTIS는 승인 대기. DBpia는 소속·교신저자를 공개하지 않아 병합하지 않음 |
| 이메일 | 수집하지 않음 | **버튼을 누를 때만** 웹에서 찾고, 출처 페이지 원문에 주소가 있는지 코드가 확인한 것만 "확인됨" 표시 | 사용자가 혼자 쓰는 도구로 범위 변경 |
| 필터 | 통학 지역 | **대학교/연구소**, **한국인/외국인(이름 기준 추정)**, 근거 있는 후보만 | 사용자 요청. 국적 데이터가 없어 이름으로 추정하며 화면에 그렇게 표시 |
| 장비 | 초록 근거만 | + **ZEUS 비공식 조회**(공개 화면, `sso_status=N`, 로그인 없음): 장비별 전국·공동활용 대수와 상위 5대 상세, 후보 소속 기관 보유 장비, 국내 후보가 연구책임자인 과제 장비. 검색 후 화면이 따로 호출 | 연구실에 장비가 없어도 공동활용 장비로 수행 가능함을 보여주기 위해. 시연용이라 robots.txt는 따르지 않음. 공식 경로는 공공데이터포털 3040771(공동활용 장비, 자동승인) |
| 후보 수 | Top 5 | 15명을 계산하고 필터 후 상위 5명 카드 + 나머지 "더 보기" | 필터를 걸어도 5명이 남도록 |

## 2. 다음 작업 (우선순위 순)

1. 데모 캐시: 예시 주제 3개 + 연구제안서 PDF 결과를 파일로 고정 (검색어가 실행마다 달라져 결과가 흔들림)
2. Vercel 배포 (키 3개: Anthropic, Voyage, OpenAlex)
3. 메일 근거 문장 3개 (초록 원문 인용 + 부분 문자열 검사) → 이메일 주소와 묶어 "보낼 첫 문단"으로
4. 적합도 경계값(0.55/0.45)을 예시 여러 개로 재조정
5. 통학 지역 필터 (기관 → 시·도 매핑)

## 3. 계획만: 교수 응답 가능성(바쁨) 평가

> 구현하지 않음. 아이디어와 설계 메모만 남긴다.

### 문제
지도교수 후보를 찾아도, 일이 많은 교수는 R&E 제안 메일에 답하지 않거나 거절하는 경우가 많다. 학생은 연락 순서를 정할 근거가 없어 답이 없을 가능성이 높은 교수부터 연락하고 시간을 잃는다.

### 무엇을 보여줄 것인가
"이 교수는 바쁘다"는 단정이 아니라, **연락 우선순위를 정하는 참고 신호**로 보여준다. 카드에 "응답 가능성 참고" 영역을 두고 근거가 된 수치를 그대로 노출한다. 점수 하나로 합치지 않는다.

### 후보 신호 (공개 데이터로 계산 가능한 것)

| 신호 | 데이터 | 해석 | 주의 |
|---|---|---|---|
| 최근 논문 생산량 | OpenAlex 최근 2년 논문 수 | 매우 많으면 대형 연구실 → 교수 본인 시간이 적을 수 있음 | 분야마다 기준이 크게 다름 → 같은 분야 안 백분위로만 표시 |
| 연구실 규모 | 최근 논문의 공저자 수, 같은 소속 공저자 수 | 대형 연구실은 학생 지도를 박사과정이 맡는 경우가 많음 (오히려 장점일 수 있음) | 해석이 양방향 |
| 동시 수행 과제 | NTIS 연구책임자 과제 수 | 과제가 많으면 바쁨 | NTIS 공개 API 범위 확인 필요 (원 계획서의 미확인 항목) |
| 직책 | 학과·기관 페이지 (학장, 센터장 등) | 보직이 있으면 응답이 늦을 가능성 | 웹 검색 필요, 정확도 낮음 |
| 고등학생 지도 이력 | 웹 검색: "R&E", "영재학교", "과학고" + 교수명 | 이력이 있으면 응답 가능성 높음 | 가장 유용하지만 데이터가 드묾 |
| 실제 응답 기록 | 학생들이 남기는 "답장 받음/거절/무응답" 기록 | 가장 직접적인 신호 | 표본이 쌓여야 의미가 생김. 교수 개인에 대한 평가로 번질 위험 → 공개 범위·익명화 정책 필요 |

### 설계 원칙
- 신호마다 근거(숫자·출처 링크)를 붙인다. 근거 없는 추정은 표시하지 않는다 (기존 근거 원칙과 같음).
- "바쁨" 같은 부정적 라벨을 공개적으로 붙이지 않는다. "연락 팁"으로 표현한다 (예: "대형 연구실 — 박사과정 연구원에게 함께 연락하면 답을 받을 가능성이 높아질 수 있음").
- 순위(0.5·T + 0.5·M)에는 섞지 않는다. 필터나 정렬 옵션으로만 쓴다.
- 실제 응답 기록은 개인정보·평판 문제가 있어 가장 나중에, 정책을 정한 뒤에만 한다.

### 검증 방법 (구현한다면)
R&E를 해본 선배들의 실제 연락 기록(누구에게 보냈고 답이 왔는지)을 모아, 위 신호들이 응답 여부와 상관이 있는지 먼저 본다. 상관이 없으면 기능을 만들지 않는다.
